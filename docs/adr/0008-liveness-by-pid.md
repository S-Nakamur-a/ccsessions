# 0008 · セッションの死活は持ち主の pid で決める。TTL は保険

採用 · 2026-07-26

## 文脈

当初はセッションの消滅を `SessionEnd` と TTL（既定 8 時間）だけで判断していた。
しかし **`SessionEnd` は「普通に終わった」ときしか飛ばない** — 強制終了・端末を
閉じる・親ツールによる kill では飛ばない。

その結果、死んだセッションが TTL のあいだ居座り、`max_sessions` の枠を食って
生きているセッションを押し出していた（実際に同じ作業ディレクトリのゾンビが 9 匹
並び、枠 12 のうち 9 を占有した）。

## 決定

`ccsessions hook` が毎回**自分の親 pid（＝ Claude Code 本体）**をセッションに記録し、
`Session::dead_reason` が `kill(pid, 0)` で生存を確かめる。TTL は保険として残す。

## 理由

「ファイルが残っている」は生きている証拠にならない。プロセスが居るかどうかだけが
確実な手掛かりになる。

## 影響

- **判定は必ず安全側（生きている）へ倒す。** `pid` が `None`（旧形式・`ccsessions set`
  由来・親を特定できなかった）なら TTL だけで判断する。`kill` が `ESRCH` を返した
  ときだけが「死」。pid の再利用もゾンビプロセスも「生きている」側に転ぶ
  （表示が少し長引くだけ）。
- **`reduce` に pid を渡さない。** pid は stdin の JSON ではなく実行環境から取る
  事実なので、reducer を純関数のまま保ち、保存直前に `hook.rs` が押す。
- 消したものは `ccsessionsd` が必ず 1 行ログに残す（`reaped session ... — pid 123 が居ない`）。
  生きているセッションが消える事故が起きたら、まずこの行を見る。
- ファイルの削除は常駐している `ccsessionsd` の仕事（起動時 + 60 秒ごと）。
  以前は `store::sweep` がどこからも呼ばれておらず、ファイルが無限に溜まっていた。
