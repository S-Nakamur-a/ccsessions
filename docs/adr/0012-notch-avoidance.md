# 0012 · ノッチは横方向に避ける

採用 · 2026-07-25 / 右優先へ変更 2026-07-25 / **右の空き幅を実行時計測へ 2026-07-28**

## 文脈

ノッチのある MacBook では画面上端の中央が物理的に欠けている。そこに帯を置くと
生き物が完全に見えなくなる。AppKit は「ノッチの矩形」を直接は教えてくれないが、
ノッチの左右で使える領域（`auxiliaryTopLeftArea` / `auxiliaryTopRightArea`）は
返すので、その隙間がノッチだと分かる。

## 決定

`bar_align` で 4 通りを選べるようにし、既定の `auto` は次のように解決する。

1. ノッチが無い、または中央に置いてもノッチに掛からないなら**中央**
2. 掛かるなら**ノッチの右**へ退避
3. 右の空き（**実行時に計測**。測れなければ見積もり 225pt）に入り切らない群れは**ノッチの左**へ

## 理由（なぜ右が先か）

当初は左を第一候補にしていたが、実測で逆にした。

- **ノッチの左は前面アプリのアプリメニュー**（アップルメニュー・File・Edit …）の
  領域。Window Server の 1 枚の窓の内部描画なので幅を測れず、**どのアプリが前面かで
  右端が動く**。メニュー項目の多いアプリが前面だと重なる。
- **ノッチの右**はメニューエクストラ（コントロールセンター・時計等）の左端までが
  空いており、ユーザが自分でアイコンを増減しない限り動かない。

つまり右の方が「他人の都合で動かない」。

> **注**: 「動かない」ことを根拠に**空き幅をベタ書きしてよい**とした結論は、下の
> [改訂 2026-07-28](#改訂-2026-07-28--右の空き幅は実行時に測る) で撤回した。
> 「右の方が他人の都合で動かない」という**この節の結論自体は今も有効**。

## 改訂 2026-07-28 · 右の空き幅は実行時に測る

**当初の判断を撤回した。** 当初はこう書いていた:

> `MENU_EXTRA_RESERVE = 225pt` は実測の見積もりであって、実行時に測った値ではない。
> 実行時に測るには `CGWindowListCopyWindowInfo` で layer=25 の窓の最小 x を引く必要が
> あり、その FFI を足すほどの価値はまだ無いと判断した。メニューエクストラが多い環境では
> 時計の下に潜り込みうるが、`bar_align` を 1 行変えれば逃げられる。

### なぜ覆ったか

**測ってみたら、安全余裕は既にゼロだった。** 同じ開発機での実測:

| | |
|---|---|
| ノッチ右端 848 → エクストラ左端 **1073** | 実際の空き **225pt** |
| 当初この ADR が根拠にした実測 | エクストラ左端 **1081** ＝ 233pt、安全側に削って 225 |
| 帯の右端（`bar_rect` の 856 ＋ 上限幅 217） | **1073** ＝ エクストラ左端 |

**クリアランス 0pt。** エクストラが 1 個増えれば確実に潜り込む。しかも
**同じ機械で 3 日のうちに 8pt 動いていた**。「ノッチの右はユーザが自分でアイコンを
増減しない限り動かない」という前提（上の「理由」節）自体は正しいが、**その「動かない
位置」が機械ごと・時期ごとに違う**以上、1 台の実測をベタ書きにすることの根拠にならない。

見送りの根拠だった「FFI を足すほどの価値」も、実際にやってみると成立しなかった:

- **画面収録権限は要らない。** 権限で伏せられるのは `kCGWindowName` だけで、
  layer / bounds / ownerPID は取れる。`CGPreflightScreenCaptureAccess() = false` の
  状態で窓 24 個中 24 個の layer が取れることを確認済み。
- **依存は増えない。** `objc2-core-graphics` は既に `ccsessionsd` の直接依存で、
  必要な関数・キー定数はすべて生成済み。
- **コストは中央値で正味 +500〜640µs**（下記）。

### 新しい決定

- **実測が取れればそれを使い、取れなければ `MENU_EXTRA_RESERVE = 225` へ落とす。**
  定数は削除せず**フォールバックに降格**する（非ノッチ機・メニューバー自動非表示・
  フルスクリーン・エクストラ 0 個）。フォールバック時の挙動は改訂前と完全に同じ。
- **`min(実測, 225)` にはしない。** エクストラが少ない環境で不当に狭める。
- **計測するのは bar 配置かつノッチありのときだけ。** dock 配置ではこの値を使わないのに、
  ドラッグ中はマウス移動ごとに `screen::metrics()` が走る。**決め手は絶対値ではない** —
  +500〜640µs は 1 フレーム 16.7ms の 3〜4% で、無条件でも「重くて壊れる」ことはまず
  起きない。使わない値のために毎フレーム払う理由が無いから条件を付ける、というだけ。
- 絞り込みは **layer=25 ／ 自プロセス除外 ／ メニューバーの帯（窓の縦中心で判定）／
  mainScreen の水平範囲**の 4 つ。**窓の名前では絞らない** — ローカライズに依存するうえ、
  `kCGWindowName` はまさに権限で伏せられる属性であり、権限に依存する条件を判定に
  持ち込まない。

### 自プロセスの除外が要である（軽い実装詳細ではない）

`ccsessionsd` 自身も layer 25 に窓を置く。除外を落とすと実測は自分の窓の左端
（＝ `notch_r + GUTTER` ＝ 856）になり、**空き幅が 225 から 8 に化ける**。8 は
「もっともらしい小さい値」なので目視では気づけない。さらに悪いことに、

1. 空き 8pt → `resolve_align` が群れをノッチ**左**へ逃がす
2. 左へ移ると自分の窓がノッチ右から消える → 実測が取れず定数 225 に戻る
3. → 右へ戻る → 1 に戻る

で **10 秒周期の左右振動**になる。`kCGWindowOwnerPID` による除外はこの経路を
断つためのものであって、ついでの絞り込みではない。

### 「実測が小さすぎたら信用しない」という下限は設けない

エクストラが本当にノッチのすぐ右まで来ている環境では、**ノッチ左へ逃がすのが
正しい挙動**である。下限はそれを潰して時計の下に潜らせるので、守りたいものと
逆の結果になる。実測が不合理に小さい事例が出たら、下限ではなく**原因側**
（どの窓を拾ったのか）をログで特定して除外条件を足す。

### 計測コストの実測値（撤回条件を後から評価できるように残す）

窓数 25、`menu_extra_left` 一式（一覧取得＋全窓走査＋最小 x 確定）:

| | 中央値 |
|---|---|
| 現行の `metrics()` 相当（`NSScreen` 読みのみ） | 126–150µs |
| `menu_extra_left` | 642–784µs |
| **正味の増分** | **約 +500〜640µs** |

**最大値（5〜7ms）を「この計測のコスト」と読んではいけない。** 呼ぶ順序を入れ替えた
対照実験で、その数 ms のテールは「sleep 明けの 1 発目」に付くものであり、`NSScreen` を
読むだけの現行 `metrics()` でも p90 3.4ms・最大 8.3ms が出る。両者に共通の
スケジューリング／WindowServer 往復のコールドコストで、関数固有ではない。
走査は **O(窓数)** なので、窓の多い環境では増分も比例して伸びる（この測定は 25 窓）。
debug / release でほぼ差が無い（WindowServer への往復で律速するため）。

### 新しい撤回条件

- 実測が定数より**常に**大きい／小さいと分かったら、定数の値そのものを見直す。
- 「ずれたまま 10 秒以上戻らない」が観測されたら、ポーリング頼みをやめて
  メニューエクストラの増減を購読する（現在は `reposition` の 10 秒周期に任せている）。

## 影響

- **ノッチの左（アプリメニュー領域）は今も測れない。** Window Server の 1 枚の窓の
  内部描画なので窓一覧に幅が出ない。左へ逃がしたときに前面アプリのメニューと重なりうる
  制限は、この改訂でも解消していない。
- **複数ディスプレイ構成は未実証。** mainScreen の水平範囲で絞ってはいるが、測定機が
  ディスプレイ 1 枚構成だったため実データで踏んでいない。
- 実測値は `ccsessionsd` の起動ログに出す（画面を目視できない環境での唯一の確認手段）。
- 入り切らないときは、左へ逃がす前に**縮めて右に収める**方を先に試す
  （[0013](0013-uniform-squeeze.md)）。左は重なりうるので、縮めて右に収まるなら
  その方が安全。
- **`bar_align = "center"` を明示指定したユーザには警告する。** `auto` は自動で
  退避するが、明示指定は素通しする（ユーザの指定を勝手に覆さない）。その結果
  「設定は効いているのに何も見えない」になり得る唯一の設定なので、`ccsessionsd` の
  起動ログと `ccsessions doctor` で理由を知らせる。設定自体は禁止しない
  （外部モニタ運用では正しい選択なので）。
