# 0022 · ゾンビプロセスは「死んでいる」と判定する

採用 · 2026-07-27

[0008](0008-liveness-by-pid.md) の続き。あちらの「ゾンビは生きている側に転ぶ
（表示が少し長引くだけ）」という影響の見立てが外れていたので、そこだけ差し替える。
pid を主判定にする決定そのものは変えない。

## 文脈

0008 の判定は `kill(pid, 0)` が `ESRCH` を返したときだけを「死」とする。
`process.rs` の doc comment はゾンビ（終了したが親が `wait` していないプロセス）が
`kill` に成功を返すことを既知の限界として挙げ、**「親が回収した時点で消える」**から
実害は小さいと書いていた。この前提が成り立たない親が実在する。

実測（2026-07-27）:

- あるセッションが `wait_user` のまま 8 時間表示され続けた。`since == updated` で、
  許可待ちへ遷移した hook が最後の 1 件だった。
- 記録されていた pid は `STAT Z` / `<defunct>`、親は `conductor`。
- **同じ親の下にゾンビが十数匹溜まっていた**（古いものは 1 か月近く前から残存）。
  Conductor は子の `claude` を `wait` しないことがある。
- したがって `is_alive` は `true` を返し続け、`dead_reason` は pid 側で
  何も言えず TTL へ落ちた。回収したのは 8 時間後の TTL である
  （`ccsessionsd: reaped session … — 28800秒 無更新`）。

同じログには `— pid … が居ない` で回収できた例もある。親が `wait` するかは
終わらせ方によって変わるため、**この不具合は「たまに出る」形で現れる**。

Conductor（や同種のラッパー）を常用している間、pid 判定は当たれば速い保険に
すぎず、主判定として当てにできない。0008 が直した問題（死んだセッションが枠 12 を
食う）が、別の層で再発している。

## 決定

`process::is_alive` の判定を「プロセスが存在するか」から
**「存在し、かつゾンビでないか」**へ広げる。macOS では **libproc**
（`proc_pidinfo(pid, PROC_PIDT_SHORTBSDINFO, …)`）に問い合わせ、

- 全部読めて `pbsi_status == SZOMB` … 死
- **`ESRCH` で失敗** … 死（libproc はゾンビを「タスクが無い」として扱う）
- それ以外の失敗（`EPERM`・想定外の短い読み取り） … **生きている扱い**

とする。安全側の規律は 0008 から変えない。「分からない」を「死」に倒す経路は
増やさず、`ESRCH` と `SZOMB` だけが「死」と言い切れる証拠になる。

実測（2026-07-27、本物の Conductor 配下ゾンビ 3 匹＋作りたてのゾンビ 1 匹）:

| 対象 | `kill(pid, 0)` | `proc_pidinfo` | `sysctl` の `p_stat` |
|---|---|---|---|
| ゾンビ | `0`（生きて見える） | 失敗・`ESRCH` | `5` = `SZOMB` |
| 生きている | `0` | 成功・`SRUN` | `2` = `SRUN` |
| 他ユーザの生きたプロセス | `-1`・`EPERM` | **成功** | `SRUN` |
| 居ない / 回収済み | `-1`・`ESRCH` | 失敗・`ESRCH` | `len = 0` |

**ゾンビに対して `proc_pidinfo` が返すのは `SZOMB` ではなく `ESRCH` だった。**
この ADR の初版は「`SZOMB` を確認できたときだけ死」と書いていたが、それだけでは
1 件も検出できない。`SZOMB` の枝は sysctl 側の観測に合わせた保険として残している。

走っていた全 pid の突き合わせで、**生きているプロセスは他ユーザ所有（`kill` が `EPERM`）でも
libproc は成功**した。`ESRCH` の誤射でセッションを消す経路は見つかっていない。

## 理由

- **TTL を短くする案は採らない。** TTL が見ているのは「黙っている時間」だけで、
  許可待ちで正しく待っているセッションと死んだセッションを区別できない。今回
  凍ったのがまさに `wait_user` であり、そこを短くすると生きているセッションを
  消す事故になる。TTL は保険のままにしておく方が安全。
- **親に `wait` させる案は採れない。** 親は他ツール（Conductor）なので手が届かない。
  こちら側だけで完結する手段が要る。
- **heartbeat を別チャネルで持つ案は成立しない。** ccsessions がセッションの生存を
  知る経路は hook だけで、許可待ちの間は hook が飛ばない。心拍として使えない。
- **`waitpid` で自分が回収する案は不可。** 自分の子ではないので `ECHILD` になる。
- ゾンビは「プロセスとしては終了済みで、親が `wait` するまでプロセステーブルの
  エントリだけが残っている」状態であり、**セッションの持ち主としては確実に死んでいる**。
  `kill` が成功することは実装上の副作用にすぎず、生存の証拠ではない。
- **`sysctl(KERN_PROC_PID)` の `p_stat` を見る道は採らなかった。** ゾンビに `SZOMB` を
  直接返すことは実測できているが、`libc` は macOS 向けに `kinfo_proc`（648 バイト）を
  定義していないので、フィールド位置を手で宣言することになる。ずれても気づかず、
  しかも**「ごみを 5 と読んで生きたセッションを消す」危険側に倒れる**。libproc 側は
  `libc` が `proc_bsdshortinfo` の型を持っているので、その risk が無い。

## 影響

- **`process.rs` は POSIX のみではなくなった。** 存在確認（`kill`）は POSIX のままだが、
  ゾンビ判定は macOS 固有。`is_zombie` は `#[cfg(target_os = "macos")]` で切り、
  他 OS では常に「ゾンビではない」＝ 0008 のままの挙動を返す。Linux で必要になったら
  `/proc/<pid>/stat` の 3 番目のフィールドが `Z` かを見ることになる。
  当面 macOS 専用でよい（配布も macOS のみ — [0021](0021-distribution.md)）。
- **番人は `process.rs::a_child_nobody_waited_for_is_not_alive`。** `/usr/bin/true` を
  spawn して **`wait` せずに**（Rust の `Child` は drop でも `wait` しない）ゾンビを
  作り、`is_alive` が `false` を返すことを実プロセスで見る。子の終了を待つぶん
  タイミング依存なのでポーリングで安定させている。あわせて同じテストが
  「その時点でも `kill(pid, 0)` は成功する」ことも固定する — ここが崩れたら
  テストはゾンビではない別のものを見ている。
  ゾンビ判定を外すとこのテストが落ちることは確認済み。
- **pid の再利用はこの決定では塞がらない。** 別問題として残す。塞ぐならセッションに
  pid の起動時刻（`kp_proc.p_starttime`）も一緒に記録して照合する必要があり、
  今回の変更とは独立に判断する。
- 0008 の「ゾンビも生きている側に転ぶ」という記述は、この ADR が上書きする
  （0008 は履歴として残す）。`process.rs` の doc comment と CLAUDE.md の不変条件は
  この決定に合わせて書き換えた。
